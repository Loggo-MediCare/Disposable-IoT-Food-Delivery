# 用完即丟智慧便當 IoT｜逐段會議紀錄與設計決策日誌

> 討論日期：2026-10-18；整理及 GitHub 更新日期：2026-10-19。
> 性質：依對話順序整理的詳細 minutes，不是逐字稿。原始語音對話未提供逐句時間戳，因此採 M01–M32 議題序號，**不虛構分鐘、報價、測試結果或正式決議**。
> 角色：「提出者」為專案構想者；「助理」為提供技術建議及風險提醒的一方。
> 關聯文件：[完整專案設計紀錄](PROJECT_DESIGN_RECORD.md)。
> 狀態說明：**確認**＝提出者明確要求／接受；**候選**＝討論過但未選定；**待驗證**＝需採購、量測或實驗；**撤回**＝討論後不列為必要條件。

## 決策基線

- **最高目標（確認）**：一次性、極低成本、可直接丟棄但允許回收重用的可貼附自主移動 IoT；如同塑膠袋與精品包同樣能裝物品，但本案追求「塑膠袋等級」的低成本，而不是昂貴送餐機器人的縮小版。
- **硬性約束（確認）**：食品安全；封條破損、包裝被開啟、疑似遭人動手腳或污染時，絕對不吃，重新提供安全餐點。封條完整不保證食品一定安全。
- **成本約束（確認）**：硬體、電池、裝配、首次連線、中央系統、配送失敗與回收成本都必須算進去。
- **主要設計方法（確認）**：容錯與集中運算換取單車硬體簡化，但不得以容錯犧牲食品安全。
- **最終封條方案（確認）**：一般一次性可見破壞痕跡的紙質／塑膠防拆封條，交由收餐者目視確認；不要求 RFID、NFC、ESP32 導電感測或焊接。
- **未定**：實際 BOM、最終電池顆數、馬達種類、感測定位、通訊協定、雲端架構、單次配送成本及法規適用範圍。

## 依原始討論順序記錄

### M01｜原始發想：貼在保麗龍便當盒的輪子
**提出者**：以雙面膠貼附小型動力組於保麗龍便當盒；最初提出兩顆 servo motor、兩個輪子、一個萬向輪，使用 Raspberry Pi 或更便宜控制板，加約一美元等級藍牙或 Wi-Fi 模組。用途是讓便當自行走到生病、無法備餐的人身邊。

**助理起初的反對／提醒**：馬達推力、重心、翻覆及障礙物等問題。
**提出者回應**：當時要求「先不要考慮問題，先把 idea 記下來」。
**結果**：保留原始發想；反對意見歸檔但不提前阻止概念探索。

### M02｜輪足、關節與樓梯
**提出者**：思考牛頓定律及機械原理；在輪子上增設一或二軸關節，模仿機械手臂或人類抬腿。設想一側輪子先停止轉動、抬高約九十度、移到樓梯高度再向前跨，另一側輪子繼續配合。以輪足混合方式兼顧平地與階梯。

**助理回應**：將「抬輪、伸前、落輪」分成機構運動階段，並提醒需考慮扭力、支撐與穩定。
**提出者後續補充**：很多使用場域已有電梯，爬樓梯不一定是第一代必要功能。
**結果（候選）**：輪足爬樓梯保留為未來研究；首代優先平地輪行。所描述的單輪抬升不代表整車已能穩定跨階。

### M03｜NVIDIA Newton 與物理模擬
**提出者**：詢問 NVIDIA 是否已有把牛頓力學公式內化的模型／工具，可供關節、輪子、摩擦、運動模擬。
**助理回應**：指出 Newton 物理模擬方向，可協助建模及模擬，但實體系統仍需校正。
**結果（候選）**：模擬屬中央研發設備功能，不應直接導致每份便當搭載昂貴 GPU。需核對實際 Newton 支援能力、版本、授權及與 ROS2／模擬器整合方式。

### M04｜昂貴中央運算與廉價節點
**提出者**：借用 K3s／Kubernetes 的 master–node 比喻：Master 用 NVIDIA 設備，Node 使用 Raspberry Pi Pico、Pico W 或 ESP32。廉價節點只接收路徑、位置／方向、抬升高度、轉軸角度、PWM 或轉速等最終指令。
**助理回應**：贊成中央規劃、節點執行的分工。
**技術校正**：此為架構類比，ESP32 並非直接跑 Kubernetes worker；控制器應執行本地閉環／超時保護，中央指令也不宜僅依賴 XYZ 而缺少座標系、時序、裝置 ID 和安全限制。
**結果（確認方向）**：集中昂貴計算，降低每台一次性節點成本。

### M05｜不接受人為藍牙遙控玩具
**助理提出選項**：可考慮人工藍牙遙控作低價方案。
**提出者強烈反對**：若由人手動遙控，便成了玩具、沒有專案意義；藍牙也可用於中央系統下達命令，但核心是自主配送。
**結果（撤回）**：人工遙控不是產品定位；BLE 可作部署及維護通道，不取代自主導航。

### M06｜「用完即丟」與回收不矛盾
**提出者**：希望整組小到不起眼、便宜到丟掉不心痛；像塑膠袋，用完可以丟，也可以洗淨回收再用。可設專人回收，但不應強制回收才有經濟性。
**助理回應**：將一次性與選擇性回收並列。
**結果（確認）**：回收是選項，不是必需；要分別核算一次性與回收再用兩種情境的總成本。不可把「體積小」直接視為法規豁免。

### M07｜第一代先簡化機構
**提出者**：強調只要兩顆小馬達、兩輪、一萬向輪、廉價板子，塑膠甚至保麗龍材質，才能貼上即走。
**助理反對／提醒**：保麗龍輪易磨耗；塑膠輪可能更可靠；輪足機構大幅增加成本及複雜度。
**結果（候選）**：優先評估塑膠輪，保麗龍輪作成本／耐久對照；輪足暫緩。

### M08｜Pico 是否內建 Wi-Fi
**提出者**：詢問 Raspberry Pi Pico 是否自帶 Wi-Fi。
**助理回答**：普通 Pico 沒有 Wi-Fi，Pico W 有 Wi-Fi。
**補充**：是否有 BLE 及可用性應依具體 Pico W／Pico 2 W 型號與韌體確認，不應一概而論。
**結果（候選）**：ESP32 系列與 Pico W 系列都保留比價；需按實際型號確認 Wi-Fi、BLE、GPIO、PWM 與功耗。

### M09｜電池型號：AA、AAA
**提出者**：不是昂貴鈕扣電池，而是大量採購廉價遙控器電池；詢問「2A、4A」的大小。
**助理回答**：AA（台灣三號）較大，AAA（台灣四號）較小；一般鹼性電池標稱每顆 1.5 V。
**結果（候選）**：優先評估 AAA 的尺寸、重量、單價、放電能力；大量採購每顆約數元只是提出者的目標／印象，尚無報價證據。

### M10｜四顆 AAA 的電壓與供電
**提出者**：追問四顆四號電池到底幾伏特。
**助理回答**：四顆 1.5 V 電池串聯，標稱約 6 V。
**提出者追問**：馬達和 ESP32 要分別供電，是否需要 H-bridge、降壓器，會不會推高成本？
**校正**：四顆鹼性電池電壓會隨放電下降；ESP32 晶片通常需 3.3 V 供電，具體開發板供電入口不同。不能將 6 V 直接接到不支援的 3.3 V 腳位。馬達啟動／堵轉電流及電池內阻必須實測。
**結果（待驗證）**：電池數量與穩壓拓撲尚未定案。

### M11｜牛頓力學、啟動瞬間與平地慣性
**提出者**：認為啟動與停止需要較多能量，平地持續滾動後因慣性而較省。
**助理回應**：起步可能出現較高電流；匀速平地仍需克服滾動阻力、傳動損耗，轉彎／坡度亦增加負載。
**示範假設**：總重 0.5 kg、輪半徑 0.02 m、速度 0.2 m/s、1 s 加速、滾阻力假設約 0.098 N，總牽引力約 0.198 N。這是說明性算例，不是實測 BOM。此前對扭力、功率的數值不得視為已確認設計餘裕。
**結果（待驗證）**：需實際量測整機重量、地面材質、輪徑、峰值電流、巡航電流、續航。

### M12｜重量不應全部由提出者提供
**提出者**：要求助理主動尋找低價輕量馬達與塑膠輪的重量，不要一再詢問已可由零件規格查得的數字。
**助理回應**：承認應從零件清單及供應商資料建立重量／價格表。
**結果（待辦）**：建立有來源的 BOM：料號、批量單價、重量、尺寸、額定電壓、空載與堵轉電流、驅動方式、交期、可替代料。

### M13｜Servo 與 DC 馬達加 H-bridge
**提出者**：詢問是否「加 H-bridge 反而比不用 H-bridge 便宜」。
**助理回應**：兩顆普通 DC 減速馬達加一顆雙通道 H-bridge，總成本可能低於兩顆連續旋轉 servo，因 servo 各自含控制電路。
**反對／校正**：不能從常理直接確定便宜；還要比較減速箱、驅動板、控制精度、失效率、耗電與採購量。連續旋轉 servo 通常由脈寬訊號控制方向／速度，不需要額外 H-bridge；普通 DC 馬達要反轉通常需要驅動電路。
**結果（候選）**：優先做兩種 BOM 對照，不預設勝負。

### M14｜是否每個零件都要黏到便當
**提出者**：擔心多一個 H-bridge 就要多黏一塊板。
**助理回應**：可以將馬達驅動、控制器與電源整合在同一小底盤或 PCB，整組用雙面膠貼附。
**結果（方向）**：整合式動力貼片優於散落多塊板子；但客製 PCB 的打樣／模具／組裝費應計入量產門檻。

### M15｜ESP32 是否有 Camera
**提出者**：詢問 ESP32 是否含相機。
**助理回應**：一般 ESP32 開發板未必有相機，ESP32-CAM 等型號提供相機方案。
**提出者要求**：中央相機與車載相機兩種都要考慮，無須過早二選一。
**結果（候選）**：中央視覺、車載視覺、混合視覺三種架構都保留比較；車載影像上傳對 Wi-Fi、電池、視野與運算延遲的影響待測。

### M16｜GPS、室內定位與 AprilTag
**提出者**：詢問是否需要 GPS，以及 GPS 是否已便宜。
**助理回應**：室內 GPS 往往不適合精準定位；建議中央攝影機搭配便當上的 AprilTag／視覺標記，也可評估車載相機。
**結果（候選）**：室內首版不依賴 GPS；AprilTag、固定路徑與攝影機視野均待實驗。中央攝影機仍有安裝、隱私及遮蔽成本。

### M17｜以 UDP 丟包類比配送失敗
**提出者**：既然單車很便宜，一次配送失敗可再試一次，類似 UDP 丟包與重傳。
**助理提醒**：通訊封包重送與實體便當重新配送不同；重複指令不能使馬達多跑一段。
**建議**：命令序號、裝置 ID、有效期限、ACK、去重、逾時停止、狀態回報。
**結果（確認原則）**：允許有限失敗與重新嘗試來降低硬體要求，但需計入食物、等待時間及重送成本；不能把 UDP 當成可靠送達保證。

### M18｜容錯是降低成本，不是堆功能
**提出者**：明確表示要把「容錯」當成降低成本的方法。
**助理舉例**：不裝昂貴編碼器，改由中央相機定期校正；一台中央攝影機服務多個便當；短時間動作由 ESP32 自主執行，避免 Wi-Fi 中斷後持續失控。
**結果（確認方向）**：以軟體與共享設備替代部分單車感測器；要量化容錯成本是否真的小於硬體節省。

### M19｜食物不必燙，但仍需食品安全
**提出者**：目的只是讓人吃得到、吃得飽，不要求熱食。
**助理回應**：可不設保溫加熱功能，改研究合適的常溫配送。
**校正**：不熱不等於可任意常溫放置；食品種類、保存溫度、配送時間及污染控制仍需符合食品安全要求。
**結果（確認）**：加熱／保溫不是初版必要功能。

### M20｜撞到人是不是像丟包
**提出者**：認為極輕便當車撞到人，可能只是小小碰一下，詢問為何要視為重大問題。
**助理提醒**：不能把人體傷害當作容許的「丟包」，應限制重量、速度、接觸力。
**算例**：0.5 kg、0.2 m/s 時，平移動能 0.01 J；這只是理想算例，不能保證無害。
**提出者回應**：質疑會動的便當是否真的會嚇到人，並要求回到成本核心。
**結果**：低速、低質量是設計方向；人員安全仍屬約束，不能宣稱「一定不危險」。

### M21｜真正重大的風險：有人拆便當動手腳
**提出者**：擔心途中有人打開便當、放入不明物品；希望使用類似郵局現金袋的防拆封條，看到開封痕跡就不能吃。
**助理回應**：建議一次性防拆貼、明顯破壞痕跡、可選編號／QR。
**結果（確認）**：食品完整性是不可妥協的最高約束，收餐者見封條破損必須拒食並換餐。

### M22｜「食品安全不能容錯」
**提出者**：明確同意「硬體可以容錯，食品不能容錯」。
**助理回應**：若發現封條損壞，標記餐點不可食用，重新配送安全餐點。
**結果（確認）**：食品拒食規則不得被成功率、節省成本或 UDP 重試邏輯覆蓋。

### M23｜封條是否應由 IoT 偵測
**提出者**：詢問 ESP32 能否理解封條破損，什麼方式最便宜。
**助理提案**：攝影機辨識或導電封條接 ESP32 GPIO；拆封後電路斷開。
**助理提出的問題**：ESP32 在便當底部，封條在袋口，拉線及連接成本可能高。
**結果（候選，後續撤回電子偵測必要性）**：技術上可行但需評估導線、接點可靠度及誤報，不是既定規格。

### M24｜塑膠袋／紙袋包裝與封條導線
**提出者**：建議像麥當勞紙袋或塑膠袋包住便當，將封條繞袋口並接兩條線到 ESP32 腳位，使用類似麵包板跳線。
**提出者疑問**：是否還要焊錫設備？
**助理回應**：原型可用免焊接連接器或導電封條測試，但大規模一次性量產不能直接假設跳線夠牢固、成本最低。
**結果（探索）**：保留為電子防拆實驗構想，非初版必需。

### M25｜RFID／NFC 的替代方案
**提出者**：提出 RFID 可能更合適；詢問 reader 是否昂貴；指出 NFC 有鈕扣、卡片等形態。
**助理回應**：被動 NFC／RFID 標籤不會自行向 ESP32 報告，通常需 reader；手機可充當部分 NFC 標籤的讀取器。特殊防拆標籤需有破壞天線／迴路等設計，普通貼紙並不會自動知道被撕開。
**結果（探索）**：RFID/NFC reader 與防拆標籤的採購價格尚未確認，不能宣稱一定最便宜。

### M26｜重要轉折：為何一定要電子封條
**提出者**：重新界定需求：只要收餐者能看見紙封條或塑膠封口是否被打開，就知道不要吃；不需要 ESP32 自動感測。
**助理承認**：先前 NFC、RFID、導電封條方案過度設計，增加硬體及部署成本。
**結果（確認）**：初版採用**可見破壞痕跡的一次性防拆封條＋收餐者目視拒食**。NFC/RFID/導線／焊接均撤出初版必要清單。要避免將封條完好誤稱為食品安全的充分證明。

### M27｜超輕 IoT 不需要機身 HMI
**提出者**：詢問沒有螢幕、按鍵的人機介面要怎麼控制馬達。
**助理回應**：手機或電腦網頁作中央操作介面；NVIDIA／雲端規劃目的地；ESP32 只接收短動作指令並控制 PWM／H-bridge。人機介面不需要黏在便當上。
**結果（確認方向）**：HMI 外置，便當模組不配置螢幕。

### M28｜首次部署 BLE、Wi-Fi 與 USB
**提出者**：關心每個便當第一次連線時是否要輸入 Wi-Fi；提議便宜藍牙作手機配對／部署，避免每次接 USB 或 micro USB。
**助理建議**：BLE 初始設定，手機傳 Wi-Fi 資訊，設備連到本地中央系統或雲端。
**助理曾提案**：預先燒錄 Wi-Fi 帳密以降低操作。
**提出者反對**：硬編碼帳密使換網路、資安與部署流程變得麻煩。
**結果（確認方向）**：BLE／手機設定優先於人工重新燒錄；實際安全配對、憑證與恢復原廠設定流程仍需設計。

### M29｜掃描、配對、上網、自動註冊
**提出者**：希望只要「貼輪子、手機掃／連 Bluetooth、選 Wi-Fi、輸入密碼」，主機甚至可在雲端；不希望部署需要工程師。
**助理回應**：以即貼即用的 onboarding 為目標；完成配網後自動連線及註冊。
**補充風險**：Wi-Fi 密碼不能明文公開或跨裝置共用；BLE 配對須避免陌生人任意接管；離線重試與憑證更新需要最低限度機制。
**結果（方向）**：低部署工時是重要成本子目標，但不是最高產品目標。

### M30｜再次確認優先級
**提出者**：強調「用完即丟」才是 top priority，不要把 plug-and-play 說成最高目標。
**助理修正**：部署容易只是服務於低單次成本。
**結果（確認）**：任何新功能都需回答「能否降低每次安全成功配送的總成本？」

### M31｜英文重申最高約束
**提出者**：「The most top target」是 disposable；「the most top constraint」是 food security；「If the food is opened, if the seal is broken, never eat it」。
**助理回應**：成本與食品安全必須同時納入規格，前者為優化目標，後者為不得違反的硬性條件。
**結果（確認）**：安全封條破損直接拒食，不得因裝置仍能運動而繼續交付餐點供食用。

### M32｜文檔交付、Google Drive 改 GitHub
**提出者**：要求完整記錄，包括助理所有反對意見與成本，最初希望電子郵件格式及 Google Docs，後改 GitHub，並要求越詳細越好。
**執行過程**：Google Drive 建檔遇到 403 權限問題；GitHub 新儲存庫建立後曾暫時未授權 ChatGPT 連接器，後續已授權成功。
**GitHub 目標**：Loggo-MediCare/Disposable-IoT-Food-Delivery，private，main 分支；既有 docs/PROJECT_DESIGN_RECORD.md 保留。本檔補上依討論順序的詳細 minutes。
**結果**：本檔記錄討論演進，不把討論中的假設寫成已量產決策。

## 成本、重量、能源與採購記錄欄位（尚無報價，不得填假數字）

每項零件至少紀錄：候選型號、供應商 URL、幣別、數量級（1／100／1000／10000）、單價、重量 g、外形尺寸、工作電壓、峰值電流、耗電、採購日期、運費稅費、替代品與供貨風險。

| 成本類別 | 內容 | 為何必要 |
|---|---|---|
| 機構 | 兩輪、萬向輪、馬達支架、底盤、雙面膠 | 不能只計馬達價 |
| 驅動 | 兩顆連續旋轉 servo 或 DC 減速馬達＋雙 H-bridge | 比較總價 |
| 控制 | ESP32／Pico W、PCB、接頭、天線 | Wi-Fi/BLE 型號需核對 |
| 電源 | AAA 電池、電池座、穩壓／保護、線材 | 6 V 不等於直接供所有腳位 |
| 包裝 | 便當盒／袋、一次性防拆貼 | 食品安全不可省略 |
| 部署 | 手機配對、Wi-Fi 設定、註冊與失敗重試工時 | 一次性大量部署成本 |
| 共用設備 | 相機、網路、NVIDIA／雲端、伺服器維護 | 分攤到每次成功配送 |
| 失敗 | 卡住、走偏、翻覆、換餐、重送、人工處理 | 容錯是否省錢的關鍵 |
| 回收 | 收集、消毒／清潔、檢測、更換電池 | 可選但不能假設免費 |

### 成本判斷公式

- 每台一次性物料成本 = 機構 + 驅動 + 控制 + 電源 + 包裝 + 組裝。
- 每次嘗試成本 = 物料成本 + 部署工時 + 共享基礎設施攤提 + 運作成本。
- 每次**安全成功配送**成本 ≈ （所有配送嘗試總成本 + 失敗換餐／回收／人工處理成本）÷ 安全成功配送次數。
- 不可用「單台硬體很便宜」取代「每次成功且安全送達的成本低」。

## 系統介面與命令草案（僅概念，非定稿）

```text
手機：BLE 配對 → 設定 Wi-Fi → 設備註冊
                        ↓
中央相機／定位 → NVIDIA 或雲端規劃 → 網路命令
                                         ↓
                                   ESP32 / Pico W
                                         ↓
                             PWM / H-bridge / 馬達
                                         ↓
                                兩驅動輪 + 萬向輪
```

最小控制訊息可包含 `device_id`、`command_id`、`expires_at`、`linear_velocity`、`angular_velocity`、`duration_ms`；輪足版本才需要關節目標角度／高度。實際封包格式、加密、序號儲存與時鐘同步待設計。BLE 主要用於首次配網，Wi-Fi 用於正常運作；中央可部署在現場或雲端，但要處理失聯及本地停止。

## 第一代原型的可驗證門檻

1. 兩個馬達、兩輪、一萬向輪在不同平整地面可低速前進、轉彎、停止。
2. 實測空載與裝餐後重量、重心、滾阻、峰值／平均電流、10 m 配送耗電。
3. 比較 2／3／4 顆 AAA 的供電方案時，**先檢查電壓與安全**，不得直接接錯 ESP32 腳位。
4. Servo 與 DC＋H-bridge 的單價、組裝工時、故障率、控制效果有實際對照。
5. BLE 初次配網可由一般使用者完成，記錄秒數、步驟與失敗率。
6. Wi-Fi 斷線／命令重複／命令過期時，小車不會無限制持續前進。
7. 一次性防拆封條能讓一般收餐者清楚辨認撕開痕跡；破損即拒食。
8. 食品保存條件及配送環境需另外符合適用安全規範。
9. 量測安全成功率後，再判斷「廉價硬體＋重試」是否真的比高可靠硬體便宜。
10. 若中央攝影機看不到小車，需明確定義停車、等待、求援或放棄，不可盲走。

## 待確認的關鍵問題

- 首版是在室內住家、醫院、照護中心，還是公共道路？場域不同，法規、安全及導航成本不同。
- 目標量產數量、每台成本上限、每次配送距離、最長可接受時間是多少？
- 使用鹼性 AAA 還是其他電池？一次性電池的回收與廢棄管理如何處理？
- 實際馬達及 H-bridge 料號、驅動板效率、電池座成本為何？
- 用 Wi-Fi 直接連雲端，或本地 gateway 再轉雲端？延遲與失聯策略為何？
- 封條由誰貼、誰檢查、破損餐點如何隔離與換餐？
- 防拆封條是「可見拆封痕跡」，不是「驗證內容未受污染」；如何訂定供餐流程？
- 一次性模組的電子廢棄物、電池處理與可選回收路徑如何設計？
