# 用完即丟智慧便當 IoT｜專案構想與設計紀錄｜2026-10-18

## 1. 最高目標

- **用完即丟**：每個便當載具在完成一次配送後即可丟棄。
- **極低成本**：單次配送硬體成本必須低到「丟掉也不心疼」。
- **可選擇回收**：不強制回收；若回收成本低於新品成本，可回收電子模組再利用。

判斷準則：任何設計決策都要回答「這會讓單次配送成本上升多少？」

## 2. 最高約束：食品安全

- **封條破損 = 絕對不能食用**，沒有例外，也不交由軟體判斷「是否還可以吃」。
- 防拆封條必須在打開時產生**不可逆**的可見破壞（撕裂、變色或斷線）。
- 電子元件（電池、馬達、電路板）與食物空間必須物理隔離。
- 若封條狀態可電子偵測（例如封條內含導線，斷線即判定開封），偵測結果只能用來**加強**警示，不能用來覆蓋肉眼可見的破損。

## 3. 硬體架構

| 元件 | 選擇 | 說明 |
|---|---|---|
| 主控 | ESP32 | 內建 Wi-Fi + BLE，單晶片完成通訊與馬達控制 |
| 驅動 | 雙馬達（差速驅動） | 左右輪速度差完成轉向，不需轉向機構 |
| 輪子 | 塑膠輪 ×2 + 萬向輪 ×1 | 三點支撐，結構最簡單 |
| 電源 | AAA 電池 | 容易取得、可丟棄；容量與電壓見第 9 節 |

設計重點：

- 差速驅動 + 萬向輪是成本最低、控制最簡單的移動底盤。
- AAA 電池電壓（單顆約 1.2–1.5 V）需確認串聯數量是否同時滿足 ESP32（3.3 V）與馬達需求，以及是否需要升壓／穩壓電路。【待補：電池顆數與電源電路】

## 4. 通訊

| 階段 | 方式 | 用途 |
|---|---|---|
| 初次設定 | BLE | 手機 App 透過 BLE 把 Wi-Fi 帳密與裝置 ID 寫入 ESP32 |
| 運行 | Wi-Fi | 與雲端／中央伺服器連線 |
| 運算 | 雲端或 NVIDIA 中央運算 | 路徑規劃、導航決策集中在伺服器，載具只執行指令 |

設計原則：**載具端愈笨愈便宜**。感知與決策盡量放到中央，載具只負責接收指令、驅動馬達、回報狀態。

【待補：中央運算選用雲端或本地 NVIDIA 主機、延遲需求、單一伺服器可服務的載具數量】

## 5. 控制

- **H-bridge**：控制馬達正反轉；雙馬達需雙通道 H-bridge（或一顆雙通道驅動 IC）。
- **PWM**：ESP32 以 PWM 調整馬達速度；左右輪 PWM 差值決定轉向。
- **自主導航**：由中央運算下發速度／方向指令，載具端執行。

【待補：H-bridge 型號、是否使用編碼器回授、導航所需的定位方式】

## 6. 容錯策略

核心思想：**用軟體容錯取代昂貴硬體**。

- 通訊採用 **UDP**：不保證送達，但由應用層處理遺失（例如指令附序號、定期重送、逾時即停止）。
- 載具失聯或逾時時，預設行為為**停止**，避免失控移動。
- **失敗即重新配送**：單次配送失敗的成本（重做一份）若低於提高可靠度的硬體成本，就接受失敗率。

## 7. 部署

- **雙面膠貼附**：電子模組以雙面膠貼在便當盒外側，不需鎖螺絲或特殊結構。
- **手機設定**：透過 BLE 由手機完成設定（見第 4 節）。
- **不需要 USB 燒錄**：韌體出廠即燒錄完成；現場只寫入設定，不更新程式。

【待補：若需更新韌體，是否採用 OTA（Wi-Fi）更新】

## 8. 未來研究

- **輪足機構**：輪子與腳的混合結構，目標是跨越門檻與上下樓梯。
- **NVIDIA Newton 物理模擬**：在模擬環境中驗證輪足機構與控制策略，再決定是否製作實體。
- **樓梯移動**：目前的輪式底盤無法上樓梯；這是輪足研究的主要動機。

這些項目會提高成本，與第 1 節「極低成本」衝突，因此列為未來研究，不納入第一版。
